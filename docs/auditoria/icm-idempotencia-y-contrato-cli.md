# ICM 0.11.4: contrato CLI e idempotencia de la proyección

Fecha de verificación: **14 de octubre de 2026**. Fuente fijada: [`rtk-ai/icm` commit `5f402434919e514109a95c6cf504427fbcef851f`](https://github.com/rtk-ai/icm/tree/5f402434919e514109a95c6cf504427fbcef851f), manifiesto [`icm-cli/Cargo.toml`](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/Cargo.toml) declara `0.11.4`. Revisé el parser y los handlers CLI, modelo `Memory`, backend SQLite y esquema de ese commit. No instalé ni ejecuté ICM.

## Contrato del CLI

Para mantener la selección de SQLite explícita y evitar la deduplicación semántica previa del comando `store`, la forma relevante es:

```sh
ICM_DB_BACKEND=sqlite icm --db "$actorDb" --no-embeddings store \
  --topic "$topic" --content "$canonicalSummary" --importance medium
```

`--db` es una opción global para SQLite y se ignora si `ICM_DB_BACKEND` selecciona Postgres u OpenSearch. `--no-embeddings` también es global. `store` recibe topic, content, importance, keywords opcionales y raw excerpt opcional; **no tiene argumento ID, clave de idempotencia ni formato JSON**. El handler crea `Memory::new`, que genera un ULID nuevo, y escribe a stdout `Stored: <id>`; una ruta de coincidencia aproximada puede escribir `Updated existing memory (similarity …): <id>`. [Parser y opciones globales](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L57-L113), [`Memory::new`](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-core/src/memory.rs#L5-L50), [handler `cmd_store`](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L3213-L3315).

El formato legible de recuperación es:

```sh
ICM_DB_BACKEND=sqlite icm --db "$actorDb" --no-embeddings recall \
  "$query" --topic "$topic" --limit 5 --format json
```

`recall --format json` emite un array JSON de memorias; vacío se representa como `[]`. Con `--no-embeddings` no se incluye `score`, y la búsqueda es léxica/por keywords. El array contiene los campos serializados de `Memory` (entre ellos `id`, `topic`, `summary`, fechas, importance, keywords y source); el serializer omite el embedding. Recall es recuperación rankeada con límite, así que un resultado vacío **no demuestra** que no exista una memoria exacta. [Parser de recall](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L135-L170), [handler de recall](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L3376-L3450), [serializer JSON](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/recall_format.rs#L157-L179).

Para enumerar memorias de un actor o topic y examinarlas en JSON:

```sh
ICM_DB_BACKEND=sqlite icm --db "$actorDb" list --format json --topic "$topic"
# O, para enumerar toda esa base:
ICM_DB_BACKEND=sqlite icm --db "$actorDb" list --format json --all
```

`list` aplica `get_by_topic` o `list_all` y comparte el serializer de recall, sin ranking de relevancia. No hay un límite por defecto si se omite `--limit`. Sirve para inspección/reconciliación por contenido, pero no expone `summary_hash` ni un campo `experienceId`. [Opciones de list](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L182-L207), [handler `cmd_list`](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L3595-L3659).

## Garantías de almacenamiento que sí existen

El backend SQLite valida/normaliza la memoria y ejecuta `BEGIN IMMEDIATE`, `store_inner` y `COMMIT` en una transacción. Si `store_inner` devuelve error, intenta `ROLLBACK`. La tabla tiene un índice único parcial sobre `summary_hash`. [Transacción de `MemoryStore::store`](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-store/src/store/memory.rs#L15-L55), [índice único](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-store/src/schema.rs#L318-L328).

Ese hash es SHA-256 de `(topic, summary)`: topic recortado y pasado a minúsculas; summary con runs de whitespace reducidos a un espacio y pasado a minúsculas; ambos se unen con NUL antes de hashear. La unicidad es por ese par normalizado, no por el ULID ni por un ID del producto. Ante un hash ya presente, `INSERT OR IGNORE` descarta el nuevo ID y retorna el ID persistido; el camino de colisión combina importancia máxima, unión de keywords y raw excerpt entrante si existe. [Normalización y hash](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-store/src/store/rows.rs#L324-L340), [colisión y retorno del ID existente](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-store/src/store/mod.rs#L284-L422).

Con embeddings activos, el handler CLI intenta antes una deduplicación aproximada dentro del mismo topic; el umbral es `0.95`, y una coincidencia fusiona resúmenes y actualiza esa memoria antes de llamar al insert exacto. Dos hechos distintos pueden ser semánticamente muy similares. `--no-embeddings` deja `memory.embedding` vacío y omite ese camino, por lo que el adaptador puede depender del índice exacto de `(topic, summary)` en vez del fuzzy merge. [Camino semántico en `cmd_store`](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L3230-L3281), [umbral y advertencia sobre similitud](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-core/src/store.rs#L55-L101).

## Qué significa para `experienceId` y una caída

ICM CLI no admite que el caller pase `experienceId`, y el ULID que recibe `Memory::new` es interno. Aunque el tipo Rust expone `Memory.id` y `MemoryStore::store` recibe una memoria completa, ese trait no define un parámetro de idempotencia por evento. El camino de colisión `INSERT OR IGNORE` consulta después por `summary_hash`; reutilizar un ID primario para un contenido distinto no es un contrato de upsert por ID y puede devolver error. [Tipo y trait](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-core/src/memory.rs#L5-L50), [contrato del trait](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-core/src/store.rs#L133-L140), [tratamiento de colisión](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-store/src/store/mod.rs#L284-L375). La unicidad de SQLite es **física para el índice de contenido normalizado**: para escrituras actuales que fijan un hash no nulo, SQLite confirma como máximo una fila por `summary_hash` en esa base. La deduplicación es **lógica por contenido**, porque dos intentos se consideran iguales si topic y summary se normalizan al mismo par. No es una garantía exactly-once por experiencia, llamada, intento ni receipt del journal.

Si la proyección define que una memoria corresponde a un par normalizado `(topic, summary)`, se puede cerrar la ventana de caída mediante outbox/replay:

1. Confirmar primero en el journal la experiencia con `experienceId` estable y el payload canónico exacto; dejar su proyección pendiente.
2. Ejecutar `store` contra la misma DB SQLite del actor, siempre con el mismo topic/summary y `--no-embeddings`.
3. Al obtener éxito, capturar el ID de stdout y escribir en una transacción del journal el receipt `experienceId → memoryId` y el estado proyectado.
4. Si cae el proceso luego del commit ICM pero antes del receipt, volver a enviar exactamente el mismo par. El índice único devuelve el mismo `memoryId`; después se registra el receipt.

Esto ofrece entrega **at-least-once con efecto idempotente por clave de contenido**, bajo estas condiciones: misma base y actor, topic/summary repetidos con la misma normalización, backend SQLite, sin fuzzy dedup habilitado y sin modificación/consolidación/eliminación concurrente del registro antes de reconciliarlo. En la configuración revisada el auto-consolidado está apagado por defecto, pero es configurable y puede reemplazar entradas; debe permanecer apagado mientras haya receipts pendientes y no se deben olvidar/podar esos registros durante la reconciliación. [Default y semántica de configuración](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/config.rs#L103-L120), [defaults](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/config.rs#L367-L374), [consolidación posterior a `store`](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L3150-L3210). La escritura y su índice son atómicos dentro de SQLite; la transacción de ICM no incluye el journal. El receipt puede retrasarse, por lo que hay consistencia eventual y replay, no atomicidad entre sistemas.

Si dos `experienceId` distintos deben conservar memorias distintas aunque topic/summary sean iguales, ICM CLI 0.11.4 no tiene el contrato necesario: su índice los colapsa al mismo ID. Si una experiencia puede producir contenido diferente entre intentos, el hash de contenido tampoco reconoce que sean el mismo evento. En esos casos se necesita una extensión de contrato/esquema con una columna o tabla de mapeo única por `experienceId` (o una herramienta propia transaccional con el journal); no declarar exactly-once apoyándose en `recall`, keywords, raw excerpt o una búsqueda de similitud.

Para reconciliar una respuesta incierta, el mecanismo preferido es repetir el `store` determinista y capturar el ID devuelto. `list --format json` puede servir como inspección forense por contenido, pero `recall` no sirve para probar ausencia y ninguna salida CLI actual proporciona una consulta exacta por `summary_hash` o por `experienceId`.

## Envelope de experiencia como clave de proyección

El contrato propuesto para S02 es **compatible con el schema de ICM sin alterarlo**, si `--content` es un `ExperienceEnvelope` JSON completo y canónico, y `experienceId` es un UUID canónico y estable dentro del propio JSON. El UUID pasa a formar parte de `summary`, que sí participa en `summary_hash`; dos envelopes con UUID distintos conservan hashes distintos aunque `content` sea idéntico. Reenviar exactamente el envelope congelado en el outbox bajo el mismo topic obtiene el `memoryId` ya insertado. Esto es encoding propio de la obra sobre deduplicación de contenido de ICM; no añade un campo/constraint nativo para IDs externos. Debe validarse en el journal que el mismo `experienceId` no se reescriba con otro payload: si la diferencia sobrevive a la normalización del hash, podría crearse otra fila; si sólo difiere por mayúsculas o runs de whitespace, ICM puede tratarla como el mismo payload y conservar la primera cadena.

La normalización del hash es global sobre el JSON string: lowercasing y colapso de runs de whitespace a un espacio. Un UUID lowercase distinto no se vuelve igual a otro por esa normalización; canonicalizar el UUID y congelar la cadena exacta evita variaciones de formato. El hash es sólo dedup key: no reescribe el JSON que el adapter almacena ni convierte campos en columnas tipadas. El store recorta whitespace exterior del topic, pero conserva el summary de entrada; rechaza summary vacío, NUL o de más de **65.536 bytes**, y exige topic no vacío, sin LF/CR/TAB y de hasta **256 bytes**. El JSON y cualquier escape UTF-8 cuentan dentro del límite byte a byte. [Validación y límites](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-store/src/store/rows.rs#L220-L295), [hash](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-store/src/store/rows.rs#L324-L340).

FTS5 indexa todo el campo `summary` junto con ID, topic y keywords, así que los tokens de los valores del envelope pueden participar en la búsqueda. ICM no parsea JSON, no indexa `experienceId`, `actorId`, `runId` o `fakeDate` como propiedades tipadas, ni filtra por sus reglas. `recall` sigue siendo rankeado y limitado; recuperar por término y luego descartar hits por actor o fecha puede omitir una coincidencia válida que quedó fuera del corte. El adapter debe parsear y validar la versión/esquema del JSON, actor/run esperado, procedencia, permisos y la ventana de fecha ficticia en **cada** resultado antes de añadirlo al contexto. Para una enumeración exhaustiva de la base se puede usar `list --format json --all`, a costa de transferir/filtrar todos los registros. [Columnas FTS5](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-store/src/schema.rs#L330-L370), [búsqueda FTS y recall limitado](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-store/src/store/memory.rs#L235-L310), [enumeración JSON](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L3595-L3659).

`--keywords` es una cadena separada por comas que CLI divide y almacena aparte; el hash sólo cubre topic y summary. El código de validación consultado no define un máximo específico de cantidad o bytes de keywords, por lo que no usarlas como ID/clave idempotente; si se rellenan, mantenerlas compactas y estables como pistas léxicas. [Parser de keywords](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L94-L113), [construcción del `Memory`](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L3213-L3228), [hash limitado a topic/summary](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-store/src/store/rows.rs#L324-L340).

Así, el envelope en `summary` resuelve la colisión entre dos experiencias de mismo texto y permite replay estable mientras la fila exista; la garantía sigue siendo de **proyección lógica por payload congelado** sobre transacciones locales de ICM. La persistencia del evento y `experienceId` en el journal sigue siendo la verdad de la obra; receipts y retry reparan la ventana de caída, pero no crean una transacción distribuida exactly-once.
