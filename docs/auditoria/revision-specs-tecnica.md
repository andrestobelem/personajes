## Resultado por frontera

La separación principal de autoridad es implementable: el journal host conserva mundo/resoluciones; cada archivo ICM aislado por corrida/personaje es una proyección de experiencias; Pi conserva contexto de intérprete. ## Ventana de crash entre sesión Pi y journal

El contrato de S02 reconoce que son almacenes distintos, pero `actor_sessions.checkpoint/eventFence` y “contexto reconciliado” requieren una operación precisa. Pi guarda entradas JSONL append-only durante la conversación, incluidas solicitudes, respuestas, tool calls/resultados y compactions; al reabrir, `SessionManager` reconstruye su leaf por los registros del archivo. `branch(id)` mueve el leaf sólo en memoria hasta que una nueva entrada de rama se escriba. No hay transacción común con `world.sqlite`. Además, el SDK declara a SessionManager autoridad sobre el contexto finalizado de Pi; asignar `session.agent.state.messages` no sustituye el contexto persistido. [Formato JSONL/árbol](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/docs/session-format.md#tree-structure), [SessionManager de contexto](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/docs/sdk.md#session-storage).

La recuperación debe tratar el leaf confirmado por el journal como fence. Secuencia sugerida, sin exigir atomicidad distribuida:

1. Antes de cada prompt, guardar en `jobs`/`actor_sessions` `jobId`, generation/epoch y `baseLeafId` del último turno Pi aceptado por el host. En la misma transacción se reserva su presupuesto.
2. Si `propose_action` escribe una propuesta en el journal, esa escritura debe ser idempotente por `(jobId, proposalSlot)` y fijar su payload hash. Repetir el mismo slot con otro payload se rechaza. Un crash después del commit de propuesta pero antes del `toolResult` de Pi se reconcilia con esa propuesta del journal; no se vuelve a ejecutar la decisión del actor.
3. Cuando Pi queda `agent_settled` y la salida ya está registrada/validada, una transacción corta guarda el estado/resultados del job y el nuevo `committedLeafId` (y su `eventFence`). No mantenerla durante una petición.
4. Si el proceso cae antes de ese commit, al recuperar abrir la sesión registrada, validar que el `baseLeafId` existe y hacer `branch(baseLeafId)` antes de crear/reanudar la sesión. Registrar un nuevo mensaje de host en esa rama antes de la próxima inferencia para que el branch elegido sobreviva en JSONL. El tail abandonado queda para auditoría, pero no entra al contexto del actor. Si la propuesta sí quedó durable, continuar desde el resultado guardado y compilar el mensaje host autorizado; si no quedó, generar un nuevo job/generation.

Este fence evita que una respuesta o tool call de un job interrumpido sea tratada como decisión confirmada. Si el archivo no contiene el leaf que el journal guardó (daño/corte de escritura), detener y reconstruir la sesión desde eventos/contexto durable o mostrar reparación; no tomar silenciosamente el último registro. S02 ya tiene las columnas necesarias en concepto, pero debe convertir esta regla en gate de recuperación P14 y vincular proposal idempotency al job antes de considerar cerrada la seam.

Al cancelar/cerrar: primero registrar cancelación/epoch en el journal, después `await session.abort()`, y finalmente `session.dispose()`. Tool processes reciben el AbortSignal; todo resultado tardío vuelve a comprobar epoch/lifecycle antes de un commit. `dispose()` solo no demuestra que la operación haya terminado. Un ICM `store` cancelado en respuesta incierta se vuelve a proyectar con el mismo envelope congelado, que es la garantía real disponible.

## ICM CLI 0.11.4: opciones invocables y límites pendientes

S02 actualizado tiene flags correctos. El comando implementable es equivalente a:

```sh
ICM_DB_BACKEND=sqlite ICM_CONFIG="$privateConfig" \
  icm --db "$actorDb" --no-embeddings store \
  --topic "$topic" --content "$canonicalEnvelope" --importance medium

ICM_DB_BACKEND=sqlite ICM_CONFIG="$privateConfig" \
  icm --db "$actorDb" --no-embeddings --read-only recall \
  "$query" --topic "$topic" --limit "$limit" --format json

ICM_DB_BACKEND=sqlite ICM_CONFIG="$privateConfig" \
  icm --db "$actorDb" --no-embeddings --read-only list --format json --all
```

`--db`, `--no-embeddings` y `--read-only` son globales. `--db` se ignora si no se fija `ICM_DB_BACKEND=sqlite`; `--read-only` evita auto-decay y access counters en `recall/list`. `ICM_CONFIG` es una vía soportada y tiene precedencia sobre config global. El proceso carga config aunque se pase `--db`; por eso el archivo privado se valida antes de arrancar. [Flags globales](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L63-L85), [config `ICM_CONFIG`](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/config.rs#L1-L12), [carga al iniciar](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L2240-L2259).

La config importa para una ventana de proyección: `auto_consolidate_enabled` es falso por default, pero configurable; en cambio `store.backup.enabled` es **true por default** y puede generar/rotar `.backup-*` durante el open de comandos de escritura. El adaptador debe fijar explícitamente qué hace con esos sidecars: desactivarlos porque el host administra snapshots, o incluirlos y mantener su retención dentro del mismo límite privado. `--no-embeddings` no reemplaza esa config. [Defaults de backup y auto-consolidación](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/config.rs#L64-L99), [open con backup](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L1654-L1689), [default de consolidación](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/config.rs#L103-L120).

`recall --limit` acepta un `usize` y por default devuelve cinco; no hay máximo host-side en el CLI. Con filtro de topic/keyword el handler amplía candidatos a diez veces el límite, con tope interno 200, y luego filtra; sigue siendo ranking, no búsqueda exacta. `--max-tokens` existe sólo como presupuesto estimado de salida de recall y no se usa en el contrato actual. `list --all` no pagina: lee todas las filas a memoria y un `--limit` opcional sólo trunca luego de leerlas. Por ello S02 puede usar list para reconciliación/forense de una DB acotada, pero el runtime no debe inferir ausencia desde recall ni enviar un `list --all` sin cota al actor. Falta fijar límites de host para query UTF-8, `limit`, timeout y bytes máximos de stdout; si se supera el máximo, descartar la salida incompleta, no parsearla como array válido. [Parser de recall/list](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L135-L205), [ampliación/corte de recall](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L3367-L3417), [enumeración list](https://github.com/rtk-ai/icm/blob/5f402434919e514109a95c6cf504427fbcef851f/crates/icm-cli/src/main.rs#L3595-L3625).

El actor sólo debe recibir resultados `recall` validados de nuevo como datos `unknown`: validar el array/Memory, parsear `summary` con el schema versionado del envelope y aplicar owner/run/ExperienceId/hash/procedencia/frontera ficticia del journal. FTS indexa texto del JSON; ICM no entiende propiedades del envelope ni hace ACL. Para historia exacta, el ledger conserva la verdad. Los límites verificados del summary (65.536 bytes UTF-8, sin NUL) y topic (256 bytes, sin LF/CR/TAB) son realmente aplicables al `--content`; `keywords` es CSV de pistas de búsqueda, fuera del hash y no sirve de clave.

## S01: esquinas de dominio que aún requieren schema

Las variantes nuevas `offer`/`acceptOffer` y contenido `gesture` mejoran el modelo, pero el inventario de IDs sólo declara `EntityHandle`; no declara `OfferId` ni `OfferHandle`. La oferta es un objeto de interacción durable con dueño, destinatario, objeto, revisión e invalidaciones, pero no aparece como tabla/evento/reducer tipado en S02. No hace falta una tabla si el event log y snapshot la proyectan, pero sí un `OfferCreated | OfferAccepted | OfferInvalidated` (u otro aggregate equivalente), handle opaco ligado a actor/run/percepción, clave de dedupe y reglas de vigencia/consumo/interrupción; sin eso todavía no se puede escribir la resolución o comprobar aceptación.

`gesture` está nombrado como variante distinta de `speech`, pero no tiene forma concreta ni catálogo/restricción de emisión para la GUI. Antes de implementar, definir un `CommunicationContent` cerrado —campos tipados para texto hablado versus gesto, y si el gesto es código de catálogo o descripción curada— y validar canal/capacidad del actor (incluido que Fang no emita speech). La intención conceptual sí está resuelta; falta contrato serializable y de presentación.

El reloj separa correctamente fecha ficticia de timestamps reales, niega avance por pulso/latencia y limita duración a números finitos. Quedan por concretar representación canónica de calendario/offset y la operación que avanza tiempo: por ejemplo, qué resultados `move`/`wait` consumen duración, cómo se trata una intervención sin duración y cuál reloj/hora se asigna a los eventos serializados concurrentemente. El host debe calcularlo determinísticamente desde estado ficticio previo y confirmar reloj, eventos y world revision en la misma transacción; no derivar fecha de `Date.now()` ni del conteo de prompts. Los `worldSeq` ordenan acontecimientos aun cuando compartan fecha ficticia.

## Presupuesto de requests en Pi: seam de `streamFunction` confirmada

La seam comprobable de Pi `1.2.0` es `session.agent.streamFunction`, instalada por el host inmediatamente después de `createAgentSession()` y antes del primer `prompt()`. `AgentSession.agent` es público; `Agent.streamFunction` es una propiedad pública mutable y contiene la función de transporte que la fábrica creó. En la fábrica SDK esa función construye las opciones de request y llama `modelRuntime.streamSimple(model, context, requestOptions)`. Guardar la referencia original y envolver esta propiedad conserva el `ModelRuntime`, el provider Codex y su resolución OAuth/API: el adaptador no construye un provider ni rehace auth. `registerProvider(providerId, config)` sólo registra/mezcla configuración del provider; `registerNativeProvider(provider)` acepta una implementación nativa completa que reemplaza/composa el provider correspondiente, por lo que no es un middleware para insertar el gate. [`AgentSession.agent`](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/core/agent-session.ts#L378-L382), [`Agent.streamFunction`](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/src/agent.ts#L113-L123), [asignación pública y constructor](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/src/agent.ts#L194-L240), [stream SDK que preserva `modelRuntime.streamSimple`](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/core/sdk.ts#L340-L365), [`streamFn` del SDK](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/core/sdk.ts#L417-L431) y [registro de providers](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/core/model-runtime.ts#L888-L949).

Cada invocación de `streamFunction` corresponde a una oportunidad de request al modelo. `agent-loop` la llama para generar cada respuesta; el loop vuelve a entrar después de tool results, así que un turno con varias rondas de tools pasa repetidamente por el mismo wrapper. La reserva se confirma antes de invocar la función original que entra al `ModelRuntime` y abre el stream de provider. El default Pi de compaction y el resumen de branch también reciben `this.agent.streamFunction`; quedan bajo el mismo gate si se invocaran. Para la política de esta obra, no exponer `compact`, resumen manual/branch/bug-report ni otra ruta secundaria de inferencia: dejar compaction automática deshabilitada y crear continuaciones como sesión nueva desde journal y memoria curados, con pausa explícita. Toda inferencia adicional que el host habilite debe pasar por la misma factory/gate. [Loop por respuesta](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/src/agent-loop.ts#L241-L253), [llamada al `streamFunction`](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/src/agent-loop.ts#L398-L409), [compaction](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/core/agent-session.ts#L2743-L2765), [branch summary](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/core/agent-session.ts#L4078-L4095).

El gate debe usar reserva durable y atómica por `(jobId, generation, requestSeq)` bajo el owner lock/CAS de S02. Antes de llamar el transporte original: comprobar el `AbortSignal`, comparar el presupuesto vigente y grabar la reserva. Si se agotó el presupuesto o falló la escritura, devolver un stream terminal de error sin llamar al original. Si se abortó antes de despachar, devolver terminal `aborted`; una reserva sólo se libera si el host puede demostrar que el transporte no se invocó. Ante crash/resultado ambiguo, la reserva permanece consumida hasta reconciliación; este conservadurismo evita sobrepasar el máximo. Si el original arrojara sin entregar stream, convertir esa excepción a error terminal y conservar el slot como intento ambiguo, en lugar de reintentar a ciegas.

Pseudocontrato del wrapper (el tipo de `original` se infiere de `session.agent.streamFunction`):

```ts
const original = session.agent.streamFunction;
session.agent.streamFunction = async (model, context, options) => {
  if (options?.signal?.aborted) return terminalAssistantStream(model, "aborted", "cancelled");
  let reservation;
  try {
    reservation = await host.reserveRequestAtomically(jobId, generation, model);
  } catch (error) {
    return terminalAssistantStream(model, "error", "request budget could not be reserved");
  }
  if (!reservation.allowed) return terminalAssistantStream(model, "error", "request budget exhausted");
  if (options?.signal?.aborted) {
    try { await host.markReservationUndispatched(reservation.id); }
    catch { /* Keep the slot reserved; failure must not reject the StreamFn. */ }
    return terminalAssistantStream(model, "aborted", "cancelled before dispatch");
  }
  try {
    // SDK callback still creates OAuth/provider headers and invokes ModelRuntime.streamSimple.
    // Explicit zero also wins over SDK provider retry defaults in buildRequestOptions().
    return await original(model, context, { ...options, maxRetries: 0 });
  } catch (error) {
    try { await host.markReservationAmbiguous(reservation.id); }
    catch { /* The durable reservation remains consumed, which is conservative. */ }
    return terminalAssistantStream(model, "error", "model transport failed");
  }
};
```

`terminalAssistantStream` debe construir `createAssistantMessageEventStream()` y emitir un único evento `{ type: "error", reason, error }`, sin `start`: el protocolo permite terminar con `error` antes de iniciar generación. `error` debe ser un `AssistantMessage` completo con `role: "assistant"`, `content: []`, `api/provider/model` del modelo, `usage` y costes cero, `stopReason` igual a `reason`, `errorMessage` seguro y `timestamp`. No se debe lanzar ni devolver Promise rechazada: el contrato `StreamFn` explícitamente lo prohíbe para errores de request/model/runtime y exige codificarlos en el stream. El `agent-loop` no captura el rechazo de `await streamFunction(...)`; `agentLoop()` sólo cierra su EventStream exterior con el handler de resolución `.then(...)`, por lo que una excepción podría dejar el prompt/stream sin cierre y saltarse la ruta normal de errores. [Contrato `StreamFn`](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/src/types.ts#L19-L37), [el `.then` exterior no maneja rechazo](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/src/agent-loop.ts#L38-L60), [protocolo de `AssistantMessageEventStream`](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/src/types.ts#L785-L817), [factory de stream terminal](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/src/utils/event-stream.ts#L91-L134).

En `SettingsManager.inMemory`, fijar `retry: { enabled: false, maxRetries: 0, provider: { maxRetries: 0 } }` y `compaction: { enabled: false }`. El nivel `retry.enabled` corta el reintento del agente y los reintentos de helpers de resumen; `retry.provider.maxRetries: 0` alimenta el builder del SDK, y el `maxRetries: 0` explícito en la llamada original protege el request incluso si se suministrara una opción distinta. El campo es parte de las opciones stream reales. No abrir otras rutas Pi con retry configurable ni confiar en que `prompt()` implica una única solicitud. [SettingsManager in-memory](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/core/settings-manager.ts#L356-L362), [aplicación de retry provider por el builder](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/core/sdk.ts#L340-L353), [opción `maxRetries`](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/src/types.ts#L190-L205), [defaults y nombres de settings](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/docs/settings.md#network-and-retries).

Dictamen: la fuente de Pi confirma un punto de veto previo al transporte, por tanto queda resuelta la duda de viabilidad que abría el hallazgo anterior. La garantía depende de que el host instale el wrapper antes de cualquier inferencia y no entregue una referencia/sesión Pi sin envolver; también depende de que la reserva use la transacción/CAS serializada del host. Esto prueba la ruta por código fuente, no ejecución runtime ni un test de no-despacho. La configuración de retry/compaction que S03 añadió es compatible; el control de error debe usar el stream terminal descrito aquí, nunca `throw` por agotamiento.

La forma de terminar por error en Pi 1.2.0 está especificada con precisión: el evento es `{type:"error", reason: Extract<StopReason,"aborted"|"error">, error: AssistantMessage}`. Un error puede ser terminal antes de `start`. Al llamar `AssistantMessageEventStream.push(errorEvent)`, el stream marca `done`, resuelve `result()` con `error` y entrega el evento al iterador; no hace falta llamar además a `end()`. `end()` sin resultado no entrega el evento terminal ni resuelve el resultado final. La interfaz `StreamFn` requiere un `AssistantMessageEventStream` y prohíbe lanzar/rechazar ante fallos de request/runtime. Por tanto, S03 es implementable si el adapter emite el evento tipado terminal por `push()` y no convierte agotamiento, cancelación pre-dispatch o errores del transporte en excepciones del wrapper. [`AssistantMessageEvent` y su razón formal](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/src/types.ts#L785-L817), [semántica de `push`/`end` y factory](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/src/utils/event-stream.ts#L43-L70), [stream de mensaje y finalización](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/src/utils/event-stream.ts#L91-L135), [contrato `StreamFn`](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/src/types.ts#L19-L37), [cierre exterior del agent loop](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/src/agent-loop.ts#L38-L60).

Se encontró y se cerró en la spec actual una ruta indirecta de request: Pi 1.2.0 tiene cache warming que puede llamar `ModelRuntime.streamSimple` por fuera de `agent.streamFunction`, así que el wrapper por sí solo no es una frontera completa. S03 ahora fija `cacheWarming:"off"`, exige verificar `settingsManager.getCacheWarmingMode()==="off"` al crear y reabrir la sesión, y mantiene el runtime host-owned sin extensiones/plugins. P17 exige revisar ausencia de llamadas con sesión ociosa y alrededor de tools. La sesión debe conservar esta invariante en todas sus fábricas y reaperturas; la inspección de fuente valida el bypass posible y la solución contractual, no que P17 ya se haya ejecutado.

**Bloqueo de paridad pendiente — presupuesto agregado por pulso.** S04 define `maxModelCallsPerPulse`, y su endpoint `step` convoca un pulso único. Sin embargo, las tablas S02 `jobs` y `request_reservations` sólo persisten `job_id`, generación y secuencia de request; no declaran `pulse_id` ni una relación padre pulso→jobs de actor. S03 describe reservas por `(jobId,generation,requestSeq)` dentro de instancias de actores. La fuente SDK confirma que cada tool round vuelve a `streamFunction`, pero ese gate sólo puede aplicar el máximo agregado del pulso si el host puede identificar, incluso tras reinicio, a qué pulso pertenecen las reservas de todos sus actor jobs. Los contratos cotejados no definen esa asociación ni otra ruta de contador atómico por pulso; por ello, el límite por corrida sí tiene base persistente descrita, mientras la garantía del límite agregado por pulso queda sin demostrar. Antes de cerrar paridad de specs, S02/S03 deben asociar cada reserva a `pulseId`/`pulseJobId` y reservar contra contadores run+pulse en la misma transacción, o definir que el pulso es el job compartido con relación explícita entre sus actor jobs y esa identidad durable. No se modificaron las specs durante esta auditoría.

S04 también dice que el presupuesto “se libera/ajusta conforme uso observado”. Para que esa frase no debilite el techo de requests, debe interpretarse junto con S03: el slot de llamada sólo se libera ante prueba de no-dispatch; requests despachadas, ambiguas, fallidas o canceladas después del dispatch no se reciclan por timeout. La medición de uso/coste se concilia por separado y puede quedar `unknown`. Recomiendo que S04 lo diga así, con mayor precisión, en la misma actualización que resuelva el vínculo de pulso.

**Dictamen R2:** Pi 1.2.0 ofrece una seam invocable para envolver cada request de respuesta y un evento terminal válido; los settings actuales desactivan los reintentos, compaction y el bypass de cache warming. S01–S04 son implementables en esas fronteras sin cambiar el provider/OAuth, y el checkpoint `initial` sin leaf evita asumir un branch de SDK inexistente. Aún no se puede declarar completa la paridad de cuotas hasta definir el vínculo durable entre pulso y reservas de actor. No es una prueba de login, provider, runtime ni ejecución de P17/P18; esas garantías corresponden a pasos de implementación y verificación posteriores.
