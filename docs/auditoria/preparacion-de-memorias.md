# Preparación explícita de memorias privadas

Estado: 15 de octubre de 2026. Implementación en validación; no acredita una representación completa ni autenticación real.

El preflight de producción comprueba SQLite privadas ya provisionadas y no puede crearlas. Antes de este cambio faltaba una acción de operador para preparar esas bases desde la interfaz. Además, el CLI puede cerrar sus sidecars WAL al salir; la mera existencia del archivo no prueba que pueda utilizarse con la política de lectura del preflight.

`run-memory-preparation.ts` introduce un trabajo durable por corte, principal y clave idempotente. La inicialización vacía sólo corresponde a una Ready sin vida anterior. Para puestas con historia, heredadas, pausadas o detenidas se reabren bases verificadas; una base ausente o inválida bloquea la operación. El host conserva conexiones de coordinación y las cierra junto con el servicio. Consultar trabajos y reiniciar no ejecutan inicialización implícita. Preparar memoria no crea recuerdos ni llama a un modelo.

La API exige autenticación local, CSRF, clave y precondición del corte; el historial y cada trabajo se limitan al principal y run autenticados. La GUI conserva la intención incierta para reintentar con la misma clave y muestra el propósito y resultados por actor. Una barrera excluye operaciones incompatibles mientras permite consultar el trabajo.

Evidencia focal de raíz: `host-maintenance-barrier.test.ts`, `memory-preparation-http.test.ts` y `memory-preparation-ui.test.tsx`: seis pruebas aprobadas. `external-backup-validation.test.ts`: catorce aprobadas y una omitida sin CLI en esa ejecución; incluye admisión de backup anterior sin tablas auxiliares nuevas y rechazo de DDL no autorizado. `run-memory-preparation.test.ts`: seis pruebas aprobadas con CLI real, incluidas cancelación, reinicio y fallo parcial seguido de reintento. `memory-preparation-production.test.ts`: una prueba integrada aprobada con HTTP del host de producción, SQLite vacías, preflight ICM de sólo lectura, cierre/reapertura e historial durable. Regresiones de recuperación, backup y preflight con CLI real: 22 aprobadas, sin omisiones. Build: 479 módulos. El recorrido en navegador verificó inicialización explícita, gate «Memoria ICM: Cumplido», recarga, reinicio real del host y preparación nueva que conserva la base existente. El proveedor desconectado y el actor sintético mantuvieron bloqueado el inicio; no hubo inferencia ni representación. Evidencia visual: `/private/tmp/personajes-memorias-preparadas.png`. La aceptación integral sigue pendiente.

La [configuración gráfica del ejecutable ICM](configuracion-icm-del-host.md) se implementó en un corte posterior: el launcher acepta la selección local guardada y mantiene el entorno como valor inicial. Este cambio no sustituye el login OAuth de OpenAI Codex o Anthropic ni acredita que una cuenta tenga acceso al perfil solicitado.

La primera ejecución global detectó siete fallos de recuperación offline por tablas auxiliares nuevas no reconocidas. Se corrigió la admisión con DDL exacta de las dos tablas y sus índices; ALTER u objetos extra se rechazan. El ledger es operativo: un recibo nuevo posterior al backup bloquea la recuperación por divergencia, sin fusionarlo ni perder su idempotencia. Regresiones posteriores: siete pruebas de host/launcher y 27 de evaluación de recuperación aprobadas. La prueba integrada también verificó backup real con una conexión ICM ociosa abierta, SQLite vacía y trabajo/receipt íntegros.

Verificación global final con ICM 0.11.4 real: **1.205 pruebas aprobadas, cero fallos y una omisión exclusiva de Linux** (1.206 totales). TypeScript correcto; build correcto (479 módulos). Log local: `/private/tmp/personajes-memory-full-verify-r3.log`.
