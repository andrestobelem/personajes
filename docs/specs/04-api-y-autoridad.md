## Frontera y autoridad

La aplicación de escritorio sirve UI y API desde un servidor Node del host, sólo en loopback y en el origen local canónico que recibe la UI al iniciar. La API es el adaptador de entrada de casos de uso; validación de sesión, autoridad, revisión de estado, presupuesto e idempotencia se comprueba en el host y de nuevo en la transacción de dominio. La ruta nunca concede permisos por sí misma si la sesión local no está autenticada.

El API público **no** expone endpoints para que un actor llame `recall_memory`, `propose_action`, SQL, ICM, Pi, shell, internet o rutas del filesystem. Las tools de S03 son puertos internos instalados por el host en la instancia Pi correspondiente. Un objeto enviado por cliente o modelo jamás puede fijar `origin`, `role`, `authority`, actor propietario, `sessionId`, ruta, resultado de revisión ni versión aprobada.

| Principal/capacidad | Permiso HTTP | Autoridad que produce el hecho |
|---|---|---|
| Operador local autenticado | Biblioteca; editar curación y configuración; preparar/iniciar/controlar corridas; inspeccionar; participar o dirigir por rutas distintas; operar backup/export/import y servicios de voz | El host confirma el origen `human/operator` y escribe comandos idempotentes. Un contenido textual nunca cambia el modo ni el permiso. |
| Participante humano ficticio configurado | Enviar una intervención sólo por `/interventions`, con identidad incluida en la configuración confirmada | El host deriva `speakerId` del vínculo autenticado a un participante; Escenario valida canal, presencia, audiencia y recepción. |
| Inspector opt-in de la sesión | Lectura privada explícita y limitada a una corrida/identidad/momento, independiente del modo observer/interlocutor/director | El host habilita una vista sólo para la sesión local actual; no cambia contexto, memoria ni percepción de actores. |
| Actor Pi | Ninguna identidad HTTP del API local | Sus tools internas sólo producen propuestas. Regidor verifica autoridad/canal/capacidad; Continuista revisa contenido comunicativo exacto cuando aplica; Escenario revalida y confirma efectos; distribución registra audiencia y entregas. |
| Director/Continuista/Regidor/Configurador/Narrador | Ningún endpoint público de veredicto o escritura directa | Responsabilidades internas con sesión/perfil de S03. Una revisión no confirma hechos. Narración sólo publica por el flujo idempotente autorizado al Observador tras revisiones. |
| Worker host | Ninguna cookie de operador ni entrada libre | Procesa jobs y outbox con origen `system` sólo para tareas técnicas/rutinas autorizadas. No atribuye al actor una decisión ni elude el journal. |

El canal determina la autoridad. La intervención humana de ficción y el comando directorial tienen endpoints y DTOs distintos. No hay `POST /approve` para turnos ordinarios: la aprobación de Continuista no es una decisión del operador, y una respuesta técnica de revisión nunca es diálogo. La UI puede ver estados técnicos del intento, pero el texto de una propuesta no publicada sólo se incluye en una vista de operador explícita; no se proyecta como emisión.

## Schemas de runtime y DTOs

S04 adopta **Zod** como biblioteca única de schemas runtime TypeScript para las fronteras HTTP. Cada cuerpo/query/path, respuesta discriminada y dato de persistencia que S04 defina se valida en el límite; los tipos TypeScript se derivan de `typeof Schema` mediante `z.infer`, sin interfaz paralela ni guardas manuales duplicadas. La versión concreta queda fijada en el lockfile al instalar dependencias. Todo ingreso se recibe como `unknown`; parsear JSON no lo vuelve confiable. Esquemas de requests son estrictos y rechazan claves de autoridad desconocidas. Los documentos importados preservan secciones desconocidas como contenido, pero eso no extiende los DTOs operativos.

Convención de tipos derivados:

```ts
type Brand<T, Name extends string> = T & { readonly __brand: Name };
const RunIdSchema = z.string().uuid().transform((id) => id.toLowerCase()).brand<"RunId">();
type RunId = z.infer<typeof RunIdSchema>;
```

Los schemas reales, no el ejemplo, son autoridad. IDs con significado distinto son incompatibles aunque viajen como texto: `RunId`, `CharacterId`, `SceneId`, `ProposalId`, `EventId`, `OperationId`, `JobId`, `CurationId`, `ImportId`, `ExportId`, `BackupId`, `PublicationId`, `ArtifactId`, `ChannelId`, `StreamCursor`, `SavedVoiceId`, `ProviderVoiceId`, `ProviderCatalogRef`, `VoicePreviewId` y `BindingDraftId`. `CharacterId` es un slug registrado de 1–80 caracteres `[a-z0-9-]`, conforme S01; nunca se usa directamente como ruta. Los IDs nuevos del host son UUIDv4 minúsculos; `ProposalId` y `WorldAttemptId` admiten UUIDv5 deterministas para que el replay de una tool Pi con el mismo job, generación y payload conserve las identidades semánticas distintas. `worldSeq`, `worldRevision`, `configRevision`, `streamOffset` y `jobRevision` son marcas distintas: entero no negativo seguro JS, máximo `9_007_199_254_740_991`. Hash SHA-256 es 64 hex minúsculos. No aceptar IDs de memoria ICM como IDs de evento/dominio.

Límites de wire obligatorios: body JSON normal ≤1 MiB; importación codificada ≤22 MiB y decodificada ≤16 MiB; texto de intervención ≤16 KiB UTF-8; texto de muestra TTS ≤4 KiB UTF-8; nombre visible ≤120 puntos de código; query de búsqueda ≤200 puntos de código; page size entero 1–100; arrays de selección ≤100; JSON anidado ≤32 niveles y ≤512 propiedades por objeto. Respuestas del proveedor también son `unknown`: JSON de operación ≤64 MiB, hasta 32 previews por respuesta de diseño y media decodificada ≤16 MiB por artefacto/≤64 MiB por operación. Son tech ceilings del host, no límites atribuidos al proveedor; superarlos falla la operación sin persistencia parcial ni binding. Rechazar NUL donde lo prohíba S02, números no finitos, enteros fraccionarios, duraciones negativas, referencias duplicadas y arreglos fuera de límite. No truncar. Errores indican campo/código, nunca repiten secretos ni texto privado.

`RunConfiguration`, `Dossier` y `DirectionCommand` se componen desde schemas de S01; S04 no redefine sus campos ni normaliza prosa de Markdown como canon. El body de Dirección reutiliza estrictamente la unión cerrada de payloads S01: `metaIndication` o `revokeMetaIndication` en el corte implementado; `changeCircumstance` tiene el endpoint físico descrito abajo; `reviseDramaticLine` permanece prevista. El cliente no envía `id`, `runId`, `origin` ni `expectedRevision`; el host los estampa con la sesión, el run y el ETag vigente. La configuración de sonido/voz usa las uniones canónicas `kind` de S06, no una segunda variedad regional: `SpanishVariety` `{kind:"proposed"}` o `{kind:"confirmed"}`, `AudioMode`, `SpeakerSlot`, `NarratorSlot`, `SoundEffectSlot`, `SpeechBinding` y `SoundBinding`. Sólo el host puede producir los campos de confirmación humana; la entrada de confirmación recibe la etiqueta elegida y el host deriva actor y fecha desde la sesión. La propuesta puede orientar actuación textual; Voice Design y TTS exigen `SpanishVariety.kind="confirmed"` con `source="operator"` en la configuración vigente. El límite de reformulación es entero 0–2, default 2, y `1 + maxReformulations` no puede superar tres versiones.

## Sesión local y protección HTTP

- Bind sólo a loopback (`127.0.0.1` o `::1`) en puerto asignado por el host. `Host` debe coincidir exactamente con la autoridad loopback/puerto activos y `Origin` con el origen canónico de la UI. Sin CORS wildcard ni reflexión de Origin; peticiones de origen ausente/no permitido y `Sec-Fetch-Site: cross-site` se rechazan en métodos mutables. No confiar en el nombre `localhost` resuelto por el cliente ni permitir host/puerto suministrado desde la petición.
- La navegación inicial `GET /` sirve el shell sólo al `Host` loopback/puerto canónico del proceso; respuesta contiene una capacidad aleatoria de un solo uso, TTL 60 segundos, en el documento inicial y no en URL, query, referer, header reflejable ni log. El servidor rechaza `Host` inesperado, origen cruzado y `Sec-Fetch-Site: cross-site`; la política de mismo origen impide que otra página lea el documento. `POST /api/v1/session` la intercambia sólo con `Origin` canónico y `Host` validado por cookie opaca `HttpOnly; SameSite=Strict; Path=/api/v1` (añadir `Secure` cuando el origen use TLS), y responde `200 {csrfToken,expiresAt}` por JSON UTF-8 sin eco del nonce; la UI guarda CSRF sólo en memoria. Todas las mutaciones posteriores requieren `X-CSRF-Token` coincidente. Cookie expira tras 30 min sin actividad o al cerrar la ventana; logout la revoca. No se presupone un IPC nativo que el diseño no define ni existe login con contraseña en esta API.
- La sesión establece un principal local de operador; no acepta autoridad por body/query/header. `SessionMode` es estado host-side mutable con `PUT /session/mode`: `{kind:"observer"}`, `{kind:"interlocutor",runId,participantId}` o `{kind:"director",runId,scope:{kind:"run"}|{kind:"scene",sceneId}}`. Cambiar modo requiere CSRF, `If-Match` de sesión y clave idempotente; el host valida que run, identidad humana/participante y scope existan. `internalInspector` no es modo ni permiso implícito: su opt-in temporal separado se conserva en `/observer-view`, puede coexistir con cualquiera de los modos y caduca con sesión.
- API acepta JSON UTF-8 y tipos MIME explícitos, sin `text/html`; limita bytes antes de parsear. Salida Markdown se entrega como texto y la UI la renderiza sin HTML ejecutable. CSP `default-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; connect-src 'self'`; `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` en sesión, vista privada y respuestas de credenciales. No registrar cuerpos de petición ni query de acceso privado.
- Tokens Pi/OAuth y clave ElevenLabs se guardan sólo bajo `<privateAuth>` de S02, con permisos privados del host, fuera de repo, `world.sqlite`, memoria ICM, export y backup. La única petición que acepta un secreto es `PUT /integrations/elevenlabs/credential`; usa campo `apiKey` acotado, redacción del body en middleware y logs, escritura directa a almacenamiento privado y respuesta vacía. El valor no se devuelve, no se hashea para telemetry y la UI borra su input al completar. Ningún schema de run, actor, tool, export o import acepta `apiKey`, token, razonamiento interno o ruta local.
- Respuestas son `no-store` salvo assets públicos versionados. No admitir navegación o fetch desde contenido de dossiers. El servidor no expone listener en interfaz de red. Este límite protege al proceso local frente a orígenes remotos; el aislamiento entre usuarios del mismo host sigue siendo responsabilidad de permisos del sistema operativo.

## Revisión optimista, operaciones y respuestas

Cada lectura `GET /runs/{id}` incluye `ETag` fuerte compuesto por `runId`, `configRevision` y `worldRevision` (por ejemplo `"run:<uuid>:c12:w44"`). La configuración de voz/versiones comparte `configRevision`; no crea un CAS alternativo. Curation usa `"curation:<uuid>:r3"`; job, `"job:<uuid>:r5"`; sesión, `"session:r4"`. Toda mutación de corrida/curación/job requiere `If-Match`; creación de recurso exige `If-None-Match: *` cuando lleva ID cliente. Orden del handler: autenticar sesión y CSRF, validar límites/schema, buscar `Idempotency-Key` durable en `api_operations` o `operations`, y comparar método/ruta/body canónico. Si la clave ya guardó la misma solicitud, devolver exactamente su recurso/resultado aun cuando su `If-Match` original ya sea obsoleto; si se reutilizó con otro método/ruta/body, devolver conflicto. Sólo una operación nueva evalúa `If-Match` y luego el commit vuelve a comprobar `configRevision`, `worldRevision`, `lifecycle`, `jobRevision`, generación/epoch y precondiciones. Una revisión obsoleta de operación nueva devuelve `412 PRECONDITION_FAILED` y no produce efecto. Ni `streamOffset` ni un cursor SSE sirven como ETag/CAS.

Cada `POST` que cree o cambie operación, job, evento, import, curación, voz, credencial o export requiere `Idempotency-Key` UUID; `PUT` de creación también cuando inicia job o efecto. La clave, scope estable de principal local, método/ruta, hash del body normalizado y recurso/resultado quedan en `api_operations`/`operations` antes de responder, salvo el body secreto: credenciales guardan sólo el ID de operación y su resultado, sin persistir ni hashear la clave API. Repetir la misma clave y método/ruta/body devuelve el mismo recurso/estado, incluso con ETag antiguo; devuelve `Idempotency-Replayed: true`. Reutilizarla para otra operación devuelve `409 IDEMPOTENCY_KEY_REUSE`. Para escrituras de secreto, la UI genera una clave nueva de un solo uso por envío; una repetición de ese ID sólo reproduce el resultado original, nunca intenta reemplazar otra vez el secreto. En corrida la clave se convierte en `OperationId` de S02; fuera de ella queda ligada al scope global y al ID de recurso/job. No caduca mientras exista el recurso/historia. Para una acción del actor, `ProposalId` base es independiente de la clave HTTP. Versión resuelta no se vuelve a ejecutar; otro payload requiere nueva propuesta/operación y el reintento del mismo ID devuelve resultado existente. Esta idempotencia asegura estado lógico persistido por host; no convierte llamadas a Pi, ICM, OAuth o ElevenLabs en transacción distribuida ni promete exactly-once externo. ICM sigue ledger/envelope y reconciliación at-least-once de S02. Resultado externo ambiguo no dispara retry automático TTS ni Voice Design.

Convenciones: `200` lectura/consulta o idempotent replay; `201` recurso síncrono creado; `202` operación/job aceptado, con `Location` a su estado; `204` éxito sin cuerpo; errores estables usan `application/problem+json` con `ApiProblem`. `X-Request-ID` aparece en toda respuesta. `Retry-After` sólo en límite temporal. Ningún éxito `202` significa que una acción ficticia ya se confirmó.

| HTTP | `ApiProblem.code` | Uso |
|---|---|---|
| 400 | `MALFORMED_REQUEST`, `INVALID_CURSOR` | JSON/syntax/query/cursor malformado. |
| 401 | `SESSION_REQUIRED`, `SESSION_EXPIRED`, `BOOTSTRAP_INVALID` | Falta o expiró sesión local. |
| 403 | `ORIGIN_DENIED`, `CSRF_INVALID`, `CAPABILITY_REQUIRED` | Origen, token CSRF o modo/autorización incorrectos. |
| 404 | `NOT_FOUND` | Recurso inexistente o deliberadamente oculto por autorización. |
| 409 | `IDEMPOTENCY_KEY_REUSE`, `INVALID_LIFECYCLE`, `ALREADY_TERMINAL`, `DUPLICATE_VERSION` | Recurso/operación existente incompatible. |
| 412 | `PRECONDITION_FAILED` | ETag/revisión obsoletos; volver a leer y decidir explícitamente. |
| 413 | `BODY_TOO_LARGE` | Supera límite UTF-8 del endpoint. |
| 422 | `VALIDATION_FAILED`, `RUN_NOT_READY`, `CHANNEL_UNAVAILABLE`, `PRIVATE_VIEW_NOT_ENABLED`, `SPANISH_VARIETY_UNCONFIRMED`, `VOICE_NOT_SELECTED`, `VOICE_BINDING_UNVALIDATED`, `AUDIO_DISABLED`, `SOUND_EFFECT_UNAVAILABLE` | Schema válido, invariante de dominio/precondición semántica incumplida. |

## Endpoints

Todas las rutas de API están bajo `/api/v1` (se omite el prefijo en las tablas por brevedad); `GET /` es el documento shell local, no un endpoint de API. Sólo `GET /health` es público dentro de la API; el resto requiere sesión local. Las tablas indican quién puede solicitar el caso de uso; las autoridades internas conservan el commit final.

### Historia, SSE y replay

`streamOffset` es secuencia append-only por corrida para todo cambio durable que la sesión puede observar, incluso job/outbox técnico; se asigna al confirmar en SQLite y permite reordenar notificaciones concurrentes. Mientras una corrida exista no se poda historia requerida por replay; SSE no incluye secretos o memoria privada aunque el operador activó inspector, que se obtiene por endpoint opt-in separado. Buffer de entrega en memoria máximo 256 envelopes; si se excede, cerrar el stream sin descartar del journal y dejar que cliente reconecte con `Last-Event-ID`. Heartbeat es comentario SSE sin ID.

## Contratos de job, budget y conflicto

Los trabajos de ejecución (`pulse`, actor inference, review, voice, import/export/backup/restore, OAuth/login, access-check) son recursos durables. Crear uno devuelve `202` con `jobId`, `Location`, estado inicial y ETag. El worker persiste cada transición antes del SSE. `DELETE /jobs/{id}` solicita cancelación cooperativa; estado final puede ser `canceled`, `failed` o `succeeded` según si un commit ya ocurrió, nunca se falsifica rollback tras commit. Una llamada interrumpida se marca `interrupted`; continuación crea generación nueva/epoch nuevo tras validar perfil, acceso, contexto y world revision.

El presupuesto de inferencia se reserva antes de invocar Pi. Cada request lleva PulseId/jobId durables y consume atómicamente cuota agregada de pulso y corrida según S02/S03; el ledger compartido cubre todos los roles Pi que hacen inferencia. El slot se libera sólo con prueba de no-despacho: dispatched, completed, ambiguous, timeout o cancelación posterior mantienen el slot consumido. Uso observado puede actualizar tokens/costes, nunca devolver una llamada ya iniciada a la cuota. Voice Design/TTS/SFX reservan en cambio sus cuotas durables separadas en el servicio de voz; RunView las agrega sin confundirlas con llamadas/coste del modelo. Timeout, rate limit y cancelación no se convierten en eventos dramáticos. Al agotamiento de una cuota de inferencia la corrida queda/entra en `paused` con `BUDGET_EXHAUSTED`; una cuota de audio impide sólo nueva operación de esa categoría y no altera texto/publicación. No se invoca más modelo/proveedor ni se cambia perfil. Reintento técnico requiere acción explícita, nueva generación y clave idempotente; reserva presupuesto y no duplica propuesta/evento ya resuelto. Los POST de proveedor sin idempotencia remota quedan `uncertain` ante timeout ambiguo y no se repiten automáticamente.

## Dependencias de cierre e implementación

S01/S02 actuales ya definen `DirectionCommand`, `RunConfigurationDraft` con constructor `ReadyRunConfiguration` por `validate`, `job_revision`, `api_operations` global y las secuencias/revisiones independientes. S04 las reutiliza: `validate` puede transicionar `draft→ready`; `preflight` sólo comprueba gates y no cambia lifecycle; `streamOffset` sólo ordena proyecciones y no es CAS. El access-check Pi y la prueba de conexión ElevenLabs son solicitudes live explícitas; health, validate, preflight, start y status consultan estado registrado sin activarlas.

Las rutas relativas de las tablas se resuelven bajo `/api/v1`; las respuestas sensibles son `no-store` y los textos de interfaz/confirmación se concretan en S05 sin alterar scopes, autoridad, schemas o controles definidos aquí. Proveedor/modelos/formatos y billing quedan sujetos a P21 live con credencial controlada: los contratos local y mock no acreditan acceso, precio, cardinalidad fija de previews, calidad acústica ni cancelación remota.

### Dirección física: `/runs/{runId}/circumstances`

`GET` requiere sesión Director del mismo run. Su alcance deriva de la sesión, nunca de parámetros que amplíen autoridad. Devuelve objetivos físicos filtrados, catálogo autorizado y ambiente actual, sin mentes/memoria/credenciales. Una sesión de escena sólo recibe lugares y objetivos dentro de su alcance; las puertas deben afectar exclusivamente lugares autorizados. ETag: `"circumstances:{runId}:w{worldRevision}:d{directionRevision}"`.

`POST` requiere CSRF, ese `If-Match`, `Idempotency-Key` y body estricto `changeCircumstance` de S01. Una sesión de escena no puede escribir alcance de corrida ni otra escena. El host estampa principal y operationId estable. `200 stored|existing` devuelve recibo con corte y efecto `applied {eventIds,recipientActorIds}` o `unchanged`. Un CAS obsoleto produce 412 con ambas revisiones; corrida ausente 404; clave/ID reutilizados o lifecycle/trabajo incompatible 409; operación, referencia, geometría, duplicación de objeto o alcance físico inválidos 422. Replay exacto mantiene el mismo recibo, incluso tras cerrar, sin avisos de publicación nuevos. Recuperación conserva entregas pendientes sin repetir el efecto.

## Recuperación completa y control externo — corte 48

El preview existente admite `{mode:"recover"}` para el backup local registrado; devuelve diferencias/fingerprint o blockers de compatibilidad completa. Confirmar por `POST /backups/{backupId}/restore` conserva sesión local, CSRF, ETag, clave y diff exacto; devuelve `202 HostRecoveryJob`, Location y ETag del job. El cliente no elige raíz ni aporta manifest/fingerprint como autoridad. Recover conserva identidad de las corridas; no devuelve un fork ni crea otra continuidad.

| Ruta | Autoridad y contrato ejecutado |
|---|---|
| `GET /host-recoveries/{operationId}` | Operador propietario. DTO público con backup/operación, estado, fase, revisión y código seguro; ETag `"host-recovery:<operationId>:r<revision>"`. Sin paths, principal ni secretos. Sólo lectura, incluso cuando producción está cerrada. |
| `GET /host-recoveries/{operationId}/ownership` | Mismo propietario. Gate ausente o nonce/PID diagnosticados, sin recuperar ni borrar. |
| `POST /host-recoveries/{operationId}/resume` | CSRF, clave e `If-Match` del job; body estricto con `expectedDirectoryOperationNonce?`. Si hay gate, exige el nonce observado y proceso muerto demostrado; PID activo/ambiguo bloquea. Reanudación durable de la misma operación, 202/Location/ETag; replay conserva recibo original y GET consulta el estado actual. |

Los recursos de control sobreviven fuera del journal sustituido. La admisión completa se drena antes del cierre de todos los servicios/handles; el HTTP de control permanece disponible. Tras una caída con operación pendiente, el launcher inicia únicamente control, sin aplicar ni reanudar automáticamente. Los getters no limpian ownership ni abren bases de producción. Reanudar conserva fases, IDs y confirmación ya admitida; no requiere volver a inventar otra solicitud por expiración del preview.

La reapertura invalida sesiones HTTP, CSRF y opt-ins privados; la GUI restablece autenticación local y consulta la operación conservada. No se restauran permisos de browser como identidad ficticia. Las sesiones Pi, memorias y presupuesto conservan sus contratos, sin inferencia ni TTS automáticos. Divergencia de estado completo, corrupción, tablas/archivos desconocidos, origen de otra raíz o lineage bloquean; preservar el original no autoriza rollback con pérdida desconocida. [Contrato de persistencia](02-persistencia-e-icm.md) y [evidencia/limitaciones](../auditoria/recuperacion-offline.md).

`HostRecoveryJob` distingue además `aborted/original-retained`: fallo anterior al intercambio con original acreditado y reabierto, sin declarar éxito de restore. Libera la admisión; no se agenda resume ni cuenta como operación pendiente. Un fallo que no pueda demostrar esa salida conserva control offline y reanudación explícita.

## Transferencia y restore de registros externos — corte 49

Todas las rutas mantienen operador local, ACL por principal y CSRF/clave en escrituras. El cliente no aporta paths host ni convierte checksums en autoridad. Un backup descargable es privado y contiene memoria/sesiones/medios; la GUI lo explica, conservando su diferencia con el export portable.

| Ruta | Contrato ejecutado |
|---|---|
| `POST /backup-exports` | `{backupId}` local registrado; 202 job de export. |
| `GET /backup-exports/{exportId}` | Estado y ETag sin iniciar ni regenerar. |
| `GET /backup-exports/{exportId}/download` | Sólo propietario y export succeeded; stream privado con Content-Length, SHA-256, filename seguro, backpressure y cierre del descriptor. No límite del antiguo DTO binario de 32 MiB. |
| `POST /backup-imports` | `{fileName,bytes}` acotados; 201 import en uploading, ID host y ETag. El nombre no es una ruta. |
| `GET /backup-imports/{importId}` | DTO uploading/validating/registered/failed/interrupted/cancelled, revisión y progreso. Sólo lectura. |

## Preparación explícita de memorias privadas

POST `/runs/{runId}/memory-preparations` exige sesión local, Origin, CSRF, Idempotency-Key y If-Match del corte `"memory-preparation:{runId}:c{configurationRevision}:w{worldRevision}"`. El cuerpo estricto sólo contiene expectedConfigurationRevision y expectedWorldRevision; el host deriva principal, elenco, rutas privadas y propósito. La barrera de mantenimiento permite esas consultas y la sesión, pero responde 503 HOST_MAINTENANCE_IN_PROGRESS a operaciones incompatibles. No relajar las comprobaciones del preflight al preparar memorias.

## Configuración del ejecutable ICM del host

GET `/host/icm-runtime-configuration` devuelve selección local, origen y revisión. POST `/host/icm-runtime-configuration/jobs` recibe sólo binaryPath absoluta o null y expectedRevision; exige sesión local, Origin, CSRF, Idempotency-Key e If-Match `"icm-runtime-configuration:r{revision}"`. Responde 202 con recibo inmutable, ETag y Location antes de obtener la barrera. Una clave con intención distinta entra en conflicto; repetirla conserva el recibo original después de avanzar la configuración. GET `/host/icm-runtime-configuration/jobs` y `.../jobs/{id}` consultan el historial del principal autenticado. Durante la recomposición esas lecturas y la sesión siguen disponibles sin usar el journal de producción; las demás operaciones incompatibles se bloquean. Ninguna ruta cambia proveedor ni reemplaza OAuth por una API key.

### Evidencia de acceso vencida en preflight

Un comprobante que no cubre `checkedAt` puede explicar una comprobación diferida, pero no certifica acceso vigente. El broker conserva las huellas observadas y registra ese informe bloqueado sin adjuntar el comprobante vencido o futuro como evidencia actual. La admisión de start/resume/step sigue exigiendo informe aprobado y prueba exacta vigente; guardar el diagnóstico no habilita ejecución.

La proyección pública de estructura añade `sceneLabels` (id/nombre) desde el snapshot del mismo corte, incluidas escenas cerradas. Esta metadata de presentación queda fuera del schema durable y de los hashes de estructura/fork; la consulta histórica no recurre al snapshot presente para completar etiquetas.
